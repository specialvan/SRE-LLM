4. F-005 · Rating scaling 合同 核心

问题

_service_player / _candidate_player 用了 12 个 inline magic number 把 SRE state 映射到 Elo-scale Player。 训练期和运行期都用同一套函数，但函数签名 / 常数之间**没有契约**—— 改个 18.0 就让所有已训 retention artifact 悄悄失效。

合同设计

Step 1: 12 个常数抽到 _RATING_* 模块常量（见 design.md#f-005）
Step 2: _rating_scaling_version() 返回所有常数的 SHA-256 前 12 位 hex
Step 3: 训练期把 version 写入 ArtifactMetadata.extra["rating_scaling_version"]
Step 4: 运行期 _hydrate_runtime_artifacts 对比 version；不一致则 downgrade to bootstrap + 发 artifacts.retention.scaling_mismatch WARNING + 标注 trace["artifacts"]["rating_scaling_status"] = "mismatch"

测试覆盖

  • test_rating_scaling_version_is_stable — 多次调用稳定
  • test_rating_scaling_version_changes_with_constant — monkeypatch 任意常量必须改变 hash
  • test_rating_scaling_contract_snapshot — 字节级 (mu, sigma) 快照断言（rel=1e-9）
  • test_artifact_version_mismatch_downgrades_to_bootstrap — 手工伪造老 artifact 不应被 hydrate
评审点：此合同一旦落地，所有改 _RATING_* 常数的 PR 都需附"对现有 artifact 影响评估"说明（ADR-0008 强制要求）。 snapshot 测试是最后一道闸门。
