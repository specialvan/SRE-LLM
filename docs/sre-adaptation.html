结构智能 → SRE 工程范式迁移 把 auto-decide 的 9 个模块抽象成可复用的 SRE 模式，附接口骨架

文档版本：v0.1 读者：SRE Lead · 平台架构 · Codex 本文共 9 个命名模式 P-01 ~ P-09

1 · 为什么可以迁移

自动驾驶决策与 SRE 看起来是完全不同的领域，但它们共享一个结构同构：

同构维度自动驾驶（auto-decide）SRE 平台
环境交通参与者 + 道路几何服务 + 调用链 + 集群
状态$x=(p, v, a, \mu)$ 连续流量 / 容量 / 健康度 连续
动作$u=(\delta, j)$ 低维扩缩容 / 限流 / feature flag 离散+连续
硬约束$|a|\le\mu g$, $h(x)\ge 0$SLO / 资源配额 / 错误预算
名义策略神经网络 / MPCML-driven auto-scaling / auto-tuning
保底行为刹停熔断 / 拒绝 / 只读降级
观测感知流水 + trace.jsonlmonitoring + tracing + logs

两个领域都有同一个工程痛点：上层用统计方法越做越聪明、但越聪明越容易"分布外翻车"。 同一个解法是：把结构化的硬约束嵌进执行链路，让聪明归聪明、可靠归可靠。

核心断言 自动驾驶里 T_inv 在做什么，SRE 里就需要一个同样形状的东西。 本文把这个"同样形状"形式化为 9 个命名模式，并给出可直接放进 Python/Go SRE 代码库的接口骨架。

3 · P-01 · 故障相关性图 ← InteractionIntentGraph

P-01

Incident Propagation Graph

← 模块 1 · 意图图

抽象：把故障传播表达成一个带语义权重的有向图。节点是服务/实例，边权是"A 抖动对 B 的破坏度"。 每次健康检查刷新一轮，过阈值的边驱动告警 / 降级决策。

auto-decideInteractionIntentGraph

节点 = 交通参与者；边权 = 距离核 × 朝向 × 意图冲突

w_ij = exp(−d/D0)·heading·conflict(p_i,p_j)
SREIncidentPropagationGraph

节点 = 服务/实例；边权 = 调用量占比 × 错误相关性 × SLO 敏感度

w_ij = call_share(i→j) · err_corr(i,j) · slo_sensitivity(j)
接口骨架

真实场景：订单服务降级

订单服务 A 调用库存服务 B 和支付服务 C。A→B 边权 = 0.9（RPS 高、错误高度相关、B 的 SLO 敏感），A→C = 0.4。 当 A 进入 circuit-open 状态时，blast_radius(A) = {B}——只对 B 做 traffic shaping，不动 C，避免过度降级。

采用成本
  • 需要调用链采样 + 错误率时序数据（大多数 SRE 平台已有）。
  • O(n²) 在 n > 500 服务时需加 KD-tree / 预筛（与 auto-decide 相同问题）。
  • 冷启动（无历史数据）时 err_corr 退化为 0.1 保守先验（对应 intent_conflict 的默认值）。
迁移要点 不要用几何距离直接类比调用次数。 真正的"距离核"应该是调用链跳数或错误传播延迟——这决定了当 A 抖动时 B 多久会感受到。把 D0 设成"平均传播时间 / 监测周期"的比值，就能让权重尺度跟 SLO 采集粒度对齐。

4 · P-02 · 双层 clamp ← BicycleModel jerk clamp

P-02

Double-Clamp Timeout Budget

← 模块 2 · 动力学

抽象：任何资源约束（加速度 / timeout / 带宽）都应在施加时和生效后两处钳位。单层 clamp 总会被数值误差或异常路径绕过。

auto-decideBicycleModel
  1. f() 里：若当前 a 已触顶，把 jerk 方向对应分量置 0
  2. step() 末端：对 a / v 做 clip 兜底数值累积
SREDeadline Propagation
  1. 客户端 SDK：根据父级 deadline 裁剪子调用 timeout（命令钳位）
  2. 服务端入口：再次 clip 到"本服务最大处理窗口"（末端钳位）
接口骨架
@dataclass(frozen=True)
class Deadline:
    abs_ts: float                       # epoch seconds
    max_budget_ms: int                  # 本服务的最大处理时长

    def remaining_ms(self) -> int:
        return max(0, int((self.abs_ts − time.time()) · 1000))

class RpcClient:
    def call(self, req, parent_deadline: Deadline):
        # ① 命令钳位：根据父 deadline 裁剪
        effective = min(parent_deadline.remaining_ms(), self.default_timeout_ms)
        if effective <= 0:
            raise DeadlineExceeded()
        return self._send(req, timeout_ms=effective)

class RpcServer:
    def handle(self, req):
        # ② 末端钳位：即使客户端没设或设错，本服务也 cap
        declared = req.deadline.remaining_ms() if req.deadline else 30000
        effective = min(declared, self.max_budget_ms)
        ctx = Context(deadline_ms=effective)
        return self._run(req, ctx)
真实场景：租户级 deadline

租户 A 调 gateway → authz → backend → db。每一跳都按 P-02 裁剪：哪怕 gateway 的 SDK bug 没传 deadline，backend 仍会 clamp 到自己的 max_budget_ms， 避免 A 的一次慢请求把 backend worker 吊死。这个模式是 Google SRE book 里"hedged requests"和"deadline propagation"的合并版。

迁移要点 clamp 必须用 min() 而不是 assert。 越界是正常业务情况，不是异常。工程上"出错时 fail-safe"比"出错时 fail-fast"优先——这点和动力学模型的 clamp 哲学完全一致。

5 · P-03 · 多目标势能调度 ← PotentialField

P-03

Multi-Objective Potential Scheduler

← 模块 3 · 势能场

抽象：自适应调度不是"找最优策略"，而是"把多个目标合成一个标量场，沿 $-\nabla\Phi$ 走出一个方向建议"。 硬约束（SLO / quota）不放在 $\Phi$ 里，而交给下游的 admission controller（P-06）。

auto-decidePotentialField
Φ = w_g·‖p-goal‖² + w_o·(r/d-1)² + w_i·Σw_ij/d_ij

用数值梯度给出"往哪开"的方向。

SREServiceQosField
Φ = w_lat·lat² + w_cost·cost² + w_err·err² − w_util·util

用数值梯度给出"下一步 replicas / concurrency / cache size 应该怎么调"。

接口骨架
@dataclass
class QosState:
    latency_p99_ms: float
    cost_per_hour: float
    error_rate: float
    utilization: float

@dataclass
class QosAction:
    d_replicas: int                   # 连续梯度经 round 后的离散动作
    d_concurrency: float
    d_cache_size_mb: float

@dataclass
class QosPotential:
    w_lat: float = 1.0
    w_cost: float = 0.3
    w_err: float = 20.0
    w_util: float = 0.5
    target_latency_ms: float = 100.0

    def value(self, s: QosState) -> float:
        return (
            self.w_lat  · max(0, s.latency_p99_ms − self.target_latency_ms)**2
          + self.w_cost · s.cost_per_hour**2
          + self.w_err  · s.error_rate**2
          − self.w_util · s.utilization             # 利用率越高 Φ 越低（鼓励高 util）
        )

    def grad(self, s: QosState, predictor) -> QosAction:
        """用有限差分：微扰每个动作维度，predictor 预测 Φ 变化。"""
        base = self.value(s)
        g = {}
        for dim in ["d_replicas", "d_concurrency", "d_cache_size_mb"]:
            s_next = predictor.what_if(s, {dim: 1})
            g[dim] = self.value(s_next) − base
        return QosAction(
            d_replicas=−sign(g["d_replicas"]),     # 沿 −∇Φ 方向
            d_concurrency=−g["d_concurrency"] · 0.1,
            d_cache_size_mb=−sign(g["d_cache_size_mb"]) · 64,
        )
真实场景：热点服务的 auto-tuner

晚高峰流量上来，$\Phi$ 的 $\partial/\partial \text{replicas} > 0$（更多 replicas 能压低 lat），所以 d_replicas = +1。 同时 error_rate 还低，所以不会触发 w_err 主导。扩容两个后，util 上升，$-w_\text{util}\cdot util$ 再拉低 Φ，系统趋于稳定。 硬约束不在 Φ 里：比如 "error_rate 必须 < 0.5%" 这种走 P-06 admission controller。

迁移要点 把 hard SLO 作为 penalty 塞进 Φ 是初学者最大的坑——正是 auto-decide 第一版实现踩过的（V 里塞距离项，导致规划停摆）。 正确做法：$\Phi$ 只给方向，硬约束由下游 admission/CBF 承担。

6 · P-04 · Lyapunov 式 Error-Budget burn-rate ← QuadraticLyapunov

P-04

Bounded-Decay Error Budget

← 模块 4 · Lyapunov

抽象：定义一个随时间应单调非增的标量 $V$（错误预算消耗量），监视 $\dot V$。 一旦超过衰减目标 $-\gamma V$，就迭代松弛当前变更：降级 feature flag、压低 rollout rate，直到 $\dot V$ 回到安全范围。

auto-decideQuadraticLyapunov
V = ½ q_v (v − v*)²
dV/dt ≤ 0 （硬）
dV/dt ≤ −γV （优先）
SREErrorBudgetBurnRate
V = 累积错误消耗 − 目标剩余预算
dV/dt ≤ 0 （硬 · 消耗不快于期望）
dV/dt ≤ −γV （优先 · 指数收敛回安全）
接口骨架
@dataclass
class BudgetSample:
    ts: float
    total_requests: int
    failed_requests: int

@dataclass
class BudgetLyapunov:
    slo_target: float = 0.999           # 99.9% 可用性
    window_days: int = 28              # rolling window
    gamma: float = 0.1                 # 期望指数回收速率

    def V(self, samples: List[BudgetSample]) -> float:
        consumed = sum(s.failed_requests for s in samples)
        allowed  = (1 − self.slo_target) · sum(s.total_requests for s in samples)
        deficit  = consumed − allowed                  # 超标量，可能为负
        return max(deficit, 0) ** 2 · 0.5

    def dV_dt(self, samples, dt_s) -> float:
        V1 = self.V(samples[−1:])
        V0 = self.V(samples[−2:−1])
        return (V1 − V0) / dt_s

class BudgetStabilityMonitor:
    def check(self, samples, dt_s) -> Tuple[bool, float]:
        dv = self.lyap.dV_dt(samples, dt_s)
        return (dv <= self.tol, dv)

    def metrics(self, samples, dt_s) -> dict:
        return {
            "budget_V": self.lyap.V(samples),
            "budget_dV_dt": self.lyap.dV_dt(samples, dt_s),
            "budget_target_decay": −self.lyap.gamma · self.lyap.V(samples),
        }
与传统 burn-rate alert 的差别
传统 burn-rateP-04 Lyapunov 版
衡量过去 $w$ 分钟消耗速度$V$ 与 $\dot V$ 的连续量
触发离散阈值（1x/2x/14x）连续：一旦违反 $\dot V\le 0$ 就松弛
动作发告警给人自动触发 P-07 action guard 矫正
回滚人工决定$\dot V \le -\gamma V$ 恢复后自动升档
迁移要点 Lyapunov 模型让 SLO 从"离散阈值告警"升级为"连续反馈控制"。 关键是 $V$ 必须只含一个语义（错误预算超标量），不要把 latency / cost 之类加进来——和 auto-decide 第一版 V 塞了距离项的错误完全对等。多目标走 P-03。

7 · P-05 · 容量可达集 ← ReachableSet + DeadZoneDetector

P-05

Capacity Reachable Set

← 模块 5 · 可达集

抽象：给定当前资源状态与扩缩容速率上限，在未来 $T$ 秒内能承接的最大流量是一个集合。若预测流量落在集合外，即"容量死区"——必须提前 shed / reject，而不是等 SLO 崩。

auto-decideReachableSet(state0, T)

采样控制序列 + RK4 + 凸包。输出"哪些 (px, py) 到得了"。

SRECapacityReachableSet

采样扩缩容轨迹 + 预热延迟模型 + 凸包。输出"未来 T 秒能承接的 (RPS, concurrency) 组合"。

接口骨架
@dataclass
class CapacityState:
    replicas: int
    concurrency_per_replica: int
    warm_replicas_fraction: float      # 0..1

@dataclass
class ScalingParams:
    max_scale_up_per_min: int = 10
    max_scale_down_per_min: int = 20
    warmup_seconds: int = 45

class CapacityReachableSet:
    def sample_endpoints(self, s0: CapacityState, T_sec: int, n=200):
        """返回 shape=(n, 2) 的 (max_rps, max_concurrency) 终点。"""
        rng = np.random.default_rng(0)
        pts = np.zeros((n, 2))
        steps = T_sec // 15
        for k in range(n):
            scale_actions = rng.integers(−5, 11, size=steps)
            s = s0
            for a in scale_actions:
                s = self.apply(s, a, dt=15)
            pts[k] = [self.rps(s), self.concurrency(s)]
        return pts

    def apply(self, s, action, dt_s):
        # ① 新增 replicas 经过 warmup_seconds 才可用（相当于 jerk-ramp 延迟 τ）
        new_replicas = max(1, s.replicas + action)
        delay_factor = min(1.0, dt_s / self.params.warmup_seconds)
        warm = s.warm_replicas_fraction + (1−s.warm_replicas_fraction)·delay_factor
        return CapacityState(new_replicas, s.concurrency_per_replica, warm)

class CapacityDeadZone:
    def check(self, state, forecast_rps: float, T_sec=300):
        endpoints = self.reach.sample_endpoints(state, T_sec)
        max_rps = endpoints[:, 0].max()
        return (forecast_rps > max_rps, max_rps)
真实场景：预测流量超容量

下一个 5 分钟预测 RPS = 50k，当前 CapacityState(replicas=100, concurrency=10, warm=0.9)。 采样 200 条扩容轨迹，凸包最大 RPS = 42k → dead_zone=True, headroom=-8k。 决策：现在拒绝尾部 16% 流量（graceful shed），而不是等 5 分钟后 SLO 崩。

迁移要点 Warm-up 延迟就是 SRE 版的 jerk-ramp：Pod 启动需要 45 s、container image pull 需要 30 s——这些延迟必须显式建模，否则扩容决策乐观，"已扩容=有容量"的假设会把人坑惨。

8 · P-06 · CBF 式 admission controller ← CBF-QP

P-06

Barrier-Constrained Admission

← 模块 6 · CBF-QP

抽象：客户端想申请 $u_\text{nom}$ 的资源/流量，admission controller 求一个满足所有 SLO 硬约束的最近可行值。 不等式形式，永远可行（最坏降到拒绝）。

核心不等式

对每条 SLO barrier $h_i$（如 "error_rate ≤ 0.5%"、"P99 ≤ 200ms"）：

$$ \dot h_i(x, u) + \alpha_i h_i(x) \ge 0 $$

$h_i(x) = \text{SLO threshold} - \text{current value}$，$\alpha_i$ 是类 K 函数增益。

接口骨架
@dataclass
class SloBarrier:
    name: str                                # "error_rate" / "p99_latency"
    threshold: float
    alpha: float                             # 类 K 函数增益

    def h(self, x: SystemState) -> float:
        return self.threshold − getattr(x, self.name)

    def h_dot(self, x, u: AdmissionAction, predictor, dt=30):
        x1 = predictor.what_if(x, u, horizon_s=dt)
        return (self.h(x1) − self.h(x)) / dt

@dataclass
class AdmissionAction:
    accepted_rps: float
    queue_size: int
    cache_size_mb: int

class AdmissionController:
    barriers: List[SloBarrier]
    predictor: CapacityPredictor
    fallback: AdmissionAction              # 必然可行 · 通常是"只服务 keep-alive"

    def filter(self, x, u_nom: AdmissionAction) -> AdmissionAction:
        # 快车道：所有 barrier 已满足
        if all(b.h_dot(x, u_nom, self.predictor) + b.alpha · b.h(x) >= 0 for b in self.barriers):
            return u_nom

        # 搜索：在 u_nom 周围网格找最近可行
        best, best_cost = None, float("inf")
        for cand in self._grid_around(u_nom):
            if all(b.h_dot(x, cand, self.predictor) + b.alpha · b.h(x) >= 0 for b in self.barriers):
                cost = self._cost(cand, u_nom)
                if cost < best_cost: best, best_cost = cand, cost

        return best or self.fallback
真实场景：流量塑形

客户端想发 10k RPS（$u_\text{nom}$）。barrier 1 = "P99 < 200 ms"，barrier 2 = "error_rate < 0.5%"。 predictor 告知：10k RPS 会让 P99 = 280 ms（violate h1）。 AdmissionController 搜出最近可行 accepted_rps = 7.8k，返回给客户端做 back-pressure。

这就是 AIMD / token bucket / leaky bucket 的数学上位替代：传统限流算法只回答"能不能过"，P-06 回答"最多能过多少能同时满足所有 SLO"。

迁移要点 predictor 的质量决定 admission 的质量。 在 auto-decide 里 predictor 是 BicycleModel（物理一阶原理）；在 SRE 里可以是：1) queueing theory 模型（M/M/k），2) 历史 regression，3) 一个 ML 模型。 初期用 queueing theory 就够了，不需要上 ML。

9 · P-07 · T_inv 式 Action Guard ← ControlInvariantOperator

P-07

Action Guard with Relax & Fallback

← 模块 7 · T_inv

抽象：任何"可能改动生产系统"的动作，必须经过 候选 → 硬校验 → 迭代松弛 → 保底降级 四段流水。 这比"通过/拒绝"的二元门更柔和——通过就直接通过，不通过就逐步调弱直到可接受，最坏退到 no-op。

auto-decideControlInvariantOperator.apply
  1. CBF 折叠
  2. Lyapunov 检查
  3. 降 jerk 松弛 N 次
  4. 兜底刹停
SREChangeGuard
  1. SLO admission（P-06）
  2. Lyapunov 预算检查（P-04）
  3. 降 rollout rate 松弛
  4. 兜底 revert / no-op
接口骨架
from enum import Enum

class GuardStatus(Enum):
    PASS            = "pass"                # 候选直接通过
    RELAXED_OPTIMAL = "relaxed_opt"         # 松弛后达到指数衰减目标
    RELAXED         = "relaxed"             # 松弛后满足普通约束
    NON_INCREASING  = "non_increasing"      # 边缘通过（dV/dt ≈ 0）
    FALLBACK        = "fallback"            # 松弛耗尽，回到 no-op / revert

@dataclass
class ChangeProposal:
    feature_flag: str
    rollout_pct: float                  # 当前想发布的百分比 0..100
    config_delta: dict

@dataclass
class ChangeGuard:
    admission: AdmissionController
    budget: BudgetStabilityMonitor
    relax_steps: int = 5
    gamma: float = 0.2

    def apply(self, state, proposal: ChangeProposal) -> Tuple[ChangeProposal, dict]:
        # ① 先过 admission（CBF 折叠）
        p_adm = self.admission.filter(state, proposal)

        # ② Lyapunov check
        V = self.budget.V(state.samples)
        exp_target = −self.gamma · V

        info = {"V": V, "dV_dt": None}
        p = p_adm
        dv = self.budget.dV_dt_with(state, p)
        info["dV_dt"] = dv

        if dv <= 1e-3:
            info["status"] = GuardStatus.PASS if dv <= exp_target else GuardStatus.NON_INCREASING
            return p, info

        # ③ 松弛：降 rollout_pct
        best, best_dv = p, dv
        for k in range(self.relax_steps):
            p = dataclasses.replace(p, rollout_pct=p.rollout_pct · 0.5)
            dv = self.budget.dV_dt_with(state, p)
            if dv <= exp_target:
                info.update(dV_dt=dv, status=GuardStatus.RELAXED_OPTIMAL)
                return p, info
            if dv <= 1e-3:
                info.update(dV_dt=dv, status=GuardStatus.RELAXED)
                return p, info
            if dv < best_dv: best, best_dv = p, dv

        # ④ 兜底：no-op（不改动）
        info.update(dV_dt=best_dv, status=GuardStatus.FALLBACK)
        return ChangeProposal(feature_flag=proposal.feature_flag, rollout_pct=0, config_delta={}), info
真实场景：渐进发布

团队想把新排序算法的 rollout_pct 从 10% 升到 50%。

  1. AdmissionController 说 50% 没有立即违反 SLO。
  2. BudgetLyapunov 测算：若真升到 50%，未来 30 分钟 error_rate 预计上浮 → $\dot V > 0$。
  3. 松弛：50% → 25% → 12.5%。在 25% 时 $\dot V \le -\gamma V$，status = RELAXED_OPTIMAL，返回 25%。
  4. 下一个评估周期再尝试 50%。

这个模式的价值：把"灰度发布的步长决策"从经验工程升级成数学反馈控制，还自动产出 observability（status 计数）。

迁移要点 fallback 必须是永远可行的 no-op。 在 auto-decide 里 fallback 是"刹停"（物理上恒可达）；在 SRE 里 fallback 不能是"revert"（上一版可能刚刚也有问题）， 而应该是"不变化 / 保持当前状态"——这是唯一一定可行的。

10 · P-08 · 不确定性驱动 derating ← BeliefState + WorstCaseGame

P-08

Observability-Driven Margin

← 模块 8 · 博弈

抽象：当感知 / 监控本身的不确定性升高，系统应该主动加大安全余量——而不是相信嘈杂的信号。 这把"上游数据质量"变成了"下游决策阈值"的直接输入。

关键公式
$$ \text{margin}(t) = \text{margin}_\text{base} + k_v \cdot \text{signal}(t) + k_\eta \cdot \eta_\text{obs}(t) $$

$\eta_\text{obs}$ 是监控可观测性熵：时序点缺失率、多 source 分歧度、label 噪声等归一化。

接口骨架
@dataclass
class ObservabilityState:
    missing_rate: float                  # 0..1
    source_divergence: float             # 多个 Prometheus 结果差异
    label_drift: float                   # label 分布漂移

    def entropy(self) -> float:
        """归一化到 [0, 1]。"""
        return min(1.0,
            0.5·self.missing_rate
          + 0.3·self.source_divergence
          + 0.2·self.label_drift)

@dataclass
class DeratingPolicy:
    base_margin: float = 0.05            # 5% SLO 余量
    signal_gain: float = 0.5
    entropy_gain: float = 0.2            # 熵=1 时加 20 个 pp

    def effective_margin(self, obs: ObservabilityState, signal: float) -> float:
        return (self.base_margin
              + self.signal_gain · max(signal, 0)
              + self.entropy_gain · obs.entropy())
真实场景：多源告警冲突

Prometheus A 说 error_rate = 0.3%，Prometheus B 说 0.7%（两个采样器分歧）。 source_divergence = 0.4 / 0.5 = 0.8；obs.entropy() ≈ 0.5。 DeratingPolicy 把 SLO 余量从 5% 扩到 5% + 0.2·0.5 = 15%——admission controller 在多源分歧时自动更保守， 直到运维确认了真实 error_rate，entropy 下降，余量才慢慢还回去。

迁移要点 把监控质量作为一等输入，不是二等事后告警。 这和 auto-decide 里 BeliefState.entropy 直接驱动 r_buf 的结构完全一致——"我越不确定你的意图，我就离你越远"。

11 · P-09 · 通用 control plane ← StructuralPlanner

P-09

Unified Control Plane Skeleton

← 模块 9 · Planner

抽象：所有前面的模式在一个唯一入口里按固定顺序串起来，成为平台的"决策骨架"。 外部系统只与此入口交互，这让"哪一层出了问题"可以通过 trace 精确定位。

接口骨架
@dataclass
class Observation:
    telemetry: Telemetry
    beliefs: Dict[str, BeliefState]
    state: SystemState

@dataclass
class Decision:
    admission: AdmissionAction
    change: Optional[ChangeProposal]
    trace: dict

class SreControlPlane:
    """auto-decide 对应物。外部唯一入口。"""
    graph: IncidentPropagationGraph        # P-01
    qos_potential: QosPotential              # P-03
    budget_mon: BudgetStabilityMonitor        # P-04
    capacity: CapacityDeadZone               # P-05
    admission: AdmissionController           # P-06
    guard: ChangeGuard                        # P-07
    derate: DeratingPolicy                   # P-08

    def step(self, obs: Observation, proposal: Optional[ChangeProposal]) -> Decision:
        # 1) 更新故障相关性图
        self.graph.update(obs.telemetry)

        # 2) 不确定性驱动 margin
        margin = self.derate.effective_margin(obs.state.observability, signal(obs))
        self.admission.barriers = self._barriers_with_margin(margin)

        # 3) 势能场给出名义动作
        u_nom_adm = self._nominal_from_potential(obs.state)

        # 4) admission 做 CBF 折叠
        u_adm = self.admission.filter(obs.state, u_nom_adm)

        # 5) 若有变更请求，guard 校验
        u_change, guard_info = (self.guard.apply(obs.state, proposal)
                                if proposal else (None, {}))

        # 6) 容量 dead-zone 检测 → 预告警
        dead, headroom = self.capacity.check(obs.state.capacity,
                                              obs.telemetry.forecast_rps)

        # 7) 合成决策 + trace
        return Decision(
            admission=u_adm,
            change=u_change,
            trace={
                "blast_radius": self.graph.blast_radius(obs.state.primary_service),
                "margin": margin,
                "V": self.budget_mon.V(obs.telemetry.samples),
                "dV_dt": self.budget_mon.dV_dt(obs.telemetry.samples, 30),
                "capacity_headroom": headroom,
                "capacity_dead_zone": dead,
                "guard_status": guard_info.get("status"),
            },
        )
trace 字段契约

和 auto-decide 一样，trace 是唯一真相源。固化为 JSON Schema：

{
  "ts": float,
  "blast_radius": [str, ...],
  "margin": float,
  "V": float, "dV_dt": float,
  "capacity_headroom": float,
  "capacity_dead_zone": bool,
  "admission": {"accepted_rps": float, ...},
  "guard_status": "pass|relaxed_opt|relaxed|non_increasing|fallback",
  "decision_ms": float
}
迁移要点 一个 control plane 一个 step() 入口。 把 P-01 ~ P-08 作为字段注入，Pythonic 的组合优于继承。 每个字段独立可测，整体通过 pytest + trace Golden 回归保证不变式。

14 · 反模式与陷阱

反模式 A-01 把所有 SLO 塞进一个 Φ 里。错。Φ 是"方向建议"，硬约束走 P-06。SRE 里常见错误：把 cost / latency / errors 全部加权合成一个 scalar loss，optimizer 为了总 loss 下降可以牺牲任一项——等价于 auto-decide 第一版 V 塞距离项，规划停摆。
反模式 A-02 fallback 不是恒可行的。在 SRE 里把 fallback 设成"revert 到上一版"是错的——上一版也可能有问题。正确做法：fallback 是"完全不改动"（no-op），或"只保留 health-check traffic"，这两个永远是可行的。
反模式 A-03 把 Lyapunov 用成 alert thresh。Lyapunov 的意义是连续监测 $\dot V$ 并驱动自动矫正，而不是"$V$ > 阈值发告警"——那就退化成传统 alert 了。P-04 的灵魂是和 P-07 的 guard 联动自动降 rollout。
反模式 A-04 predictor 的误差被忽略。P-06 的质量 ≤ predictor 的质量。如果 predictor 是个新的 ML 模型，必须用 P-08 derating 把它的 prediction interval 作为额外 margin 喂进去——模型越不确定，余量越大。
反模式 A-05 绕过 control plane。P-09 的设计前提是唯一入口。一旦某个业务线"因为紧急"走了旁路，所有 trace / SLO / 不变式都失效。正确做法：加一个"bypass flag"，被 bypass 的动作也走 plane、只是记一条 bypassed=true 的 trace，事后可审计。
反模式 A-06 CI 检查器当 runtime guard 用（反过来也一样）。CI 是发布时的一次性门，P-07 是每次动作的实时门——两者在概念上对齐但不可替代。P-07 必须接入运行时 metrics，CI 静态检查只是锦上添花。

一句话收尾

整套 auto-decide 给 SRE 最重要的启示不是任何单个模式，而是一句话：

核心观点 "聪明"的上层与"可靠"的下层必须解耦。 聪明归神经网络、启发式、调参器；可靠归数学不变量写进硬约束。 auto-decide 在自动驾驶里这样做，SRE 同样需要——越往 AI-driven 运维走，这层"可靠"的物理地基越是不可或缺。
