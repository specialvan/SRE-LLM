1 · 这份文档的定位

Codex 上一轮新增的 architecture.html 已经覆盖了：静态层次图 / runtime 时序 / Requirements / Task Breakdown / Refine loop。但架构评审里，有 5 种视图它没覆盖，也是下一轮继续深挖时必然要补的：

  1. 类型流图（谁产出谁消费什么数据类型）；
  2. 场景 × 模块激活矩阵（哪个场景触发哪个模块）；
  3. 失败决策树（出故障时从哪个症状回推到哪个模块）；
  4. 时延与失败预算（每个阶段的 P50/P99 + 失败率红线）；
  5. Benchmark 驱动的 refine 闭环（benchmark JSON 如何回到架构图）。
作用 这 5 张视图的目的是：当 Codex 下一轮遇到 "emergency_rate 降不下来" 或 "新加一类 barrier 应该怎么接" 时，可以不需要读全部代码，就从视图上定位到要改的边界。

2 · 类型流 · 谁生产谁消费

架构图展示"模块",但真正的"钢筋"是数据类型。下图把 9 个模块 + trace 契约按数据类型的产出/消费重新画一次。

关键洞察 VehicleParams 是 frozen dataclass，这意味着它是全局常量注入——任何模块拿到同一个 params 对象都是只读的。如果下一轮有场景需要"一个 planner 多种车型"，必须在 StructuralPlanner 里显式持有多个 params，不能在运行时 mutate。

4 · 失败决策树

出故障时怎么从"症状"倒推到"改哪里"。每个叶节点都指向一个具体模块 + 参数 + finding ID。

怎么用这棵树 出问题 → 找根因 → 找到叶节点 → 按叶节点的箭头改。 最关键的观察：B1 和 C1 都指向 "升级 nominal policy"，这说明当前 benchmark 的两个异常指标（emergency_rate / fallback_rate）同源，一次升级就能同时解决。
