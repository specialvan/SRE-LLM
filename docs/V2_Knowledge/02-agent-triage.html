Codex · 下一轮开发 agent

最主要的接手角色
目标：完成 Claude review pack 里的 action items，把 benchmark 的 SLO 违约修到达标。不扩新功能。

开工前 · 10 分钟准备

  1. 跑 pytest -q，确认 19 tests 全绿。
  2. 跑 python -m examples.compare_e2e_vs_structural --n 20 --metrics-out artifacts/m.json，亲眼看到 emergency_rate ≈ 42%。
  3. 打开 claude-review/00-executive-summary.html，5 分钟摘要。
  4. 打开 07-codex-directives.md，默念 10 DO + 10 DON'T。

开工中 · 推荐的 PR 序列

按 07-directives 的 PR 序列顺序推进，共 15 个 PR。最关键的顺序是：

  1. 先做小修：AI-03a（title mojibake）/ AI-03c（summaizer 处置）/ AI-04（schema 演进）。
  2. 再做契约：AI-03b（status 枚举） / AI-11（CI invariant scanner）。
  3. 再做 SLO 守门：AI-01（benchmark 红线，初次 xfail）。
  4. 核心升级：AI-02（PredictiveBrakePolicy，完成后去掉 xfail）。
  5. 再做回归：AI-12（非法组合测试） / AI-14（benchmark CI artifact）。
  6. 最后文档同步：AI-05/07/08/09/10/06/13。

Review Agent · 评审下一轮提交

承接 Claude 做同类工作
目标：审视 Codex round-2 提交，产出 claude-review round-3（或 gemini-review / gpt-review）。

开工前 · 读什么

  1. 本轮 findings —— 理解 Claude round-2 发现了什么，避免重复覆盖。
  2. action items —— 了解 Codex 应该完成什么。
  3. 不变式目录 —— 你的审查 checklist 基础。
  4. 合约目录 —— 判断"接口变更是否合法"的依据。

审查路径

  1. 跑 git log --oneline HEAD~N..HEAD 看 Codex 提交了哪些 PR，每个 PR 关闭哪条 AI。
  2. 按 AI 编号对照 action items 的"验收标准"，逐条打勾。
  3. 跑 pytest -q + benchmark，对比 artifacts/benchmark-metrics.json 与上一轮的差异。
  4. 扫 git diff，重点看是否触碰红区（见 Codex 指令的 DON'T 清单）。
  5. 把本轮发现汇总成 docs/claude-review-v3/（或按你的 agent 名建子目录），保持文件结构与 v2 一致。

审查时必问的 12 个问题

来自 codex-handoff.md § Reviewer Checklist：

  1. README 是否仍指向所有核心文档？
  2. planner.step() 是否仍是唯一北向入口？
  3. u_nn 是否一定经过 cbf.py？
  4. u_safe 是否一定经过 invariant.py？
  5. cbf_status 枚举是否仍符合 INV-G12？
  6. trace 是否仍能解释每次动作改写？
  7. BrakingDistanceBarrier 是否考虑速度、反应时间、摩擦？
  8. Lyapunov 是否只承担稳定性职责（未混入距离）？
  9. reachable 是否仍作为"可达下界"而非形式化证明？
  10. game 的不确定性是否仅改 buffer / derating？
  11. benchmark 是否同时报告安全、舒适度、耗时、fallback？
  12. SRE 映射是否仍在迁移"机制"而非"术语"？

成功标志

  • 新一轮 review pack 结构与 v2 一致（README / findings / action-items / directives 四件套）；
  • 历史 findings 已标记为 resolved / partially-resolved / still-open；
  • 不新增"为了看起来深入而凭空编的 finding"——每条 finding 都有代码证据。
陷阱：评审时不要只看测试是否通过。测试可以写"正好符合当前实现"但掩盖问题。要看trace / benchmark 的实际数字是否按 action items 的验收标准改善。

SRE / 平台迁移 Agent

跨域复用
目标：把 auto-decide 的 9 个模式抽象成 SRE 平台组件。不改 auto_decide 本体代码。

必读顺序

  1. sre-adaptation.html —— 9 个命名模式 P-01~P-09 的完整骨架。
  2. equations-digest §13 —— 35 方程到 SRE 的逐一对位。
  3. deep-dive §14 SRE 挂钩点汇总。

可以开始做什么

  1. 把 sre-adaptation 的 sre_control/ 目录骨架拉到一个独立 repo（不要污染 auto-decide）。
  2. 先实现 P-01 故障相关性图 与 P-04 Lyapunov burn-rate——这两个是只读模块，风险最低。
  3. 用真实 telemetry 跑一遍，产出与 trace.jsonl 同构的 observability 文件。
  4. 再上 P-06 AdmissionController 作为 shadow（不实际拒绝流量），观察 2 周。
  5. 按 采用路线图四阶段推进。

迁移原则（必守）

✅ 机制迁移把 "CBF 硬约束 + QP 求最近可行" 迁成 "admission controller"
✅ 接口同构trace / metrics JSON 的字段命名方式保持一致
❌ 术语挪用不要说"服务也有 Lyapunov 方程"，要说"错误预算是 Lyapunov 意义上的能量"
❌ 数学本体迁移不要在 SRE 里也用 bicycle model——用 queueing theory 或 ML predictor

成功标志

  • 有独立的 sre_control/ repo，目录结构与 auto_decide 对称；
  • 至少 2 个 pattern 在生产 shadow 运行；
  • 产出可与 auto-decide trace.jsonl 并列分析的 observability 数据。

必读顺序
